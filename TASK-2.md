# Task 2: the harder part

Same ledger, same rules as in [TASK.md](TASK.md) (read it first, its rules still apply). Task 1 is done on this branch; this is the second, harder round. Migration `V3__groups_and_bank_lines.sql` adds an account group tree (`account_group`, `account.group_id`) and external bank statement lines (`bank_line`). Use jOOQ's DSL for all SQL, tests against a real Postgres. Put new code next to the existing code, follow its style, and do not break the existing tests.

Reporting currency is CHF. Never add amounts of different currencies together.

1. **Group roll-up.** For a root group, return every group in its subtree with its depth, its path (`Bank / Retail / Zurich`), and per currency the sum of the balances of its own accounts and of its whole subtree. One query. Also provide "move group under another parent": it must reject a move that would create a cycle, even when two moves run concurrently.
2. **Average daily balance.** For each account, for one calendar month (UTC): the balance at the end of every day, including days without postings, and from that the average daily balance and the lowest day-end balance. One query, no loop over days in Java. A day's balance includes everything booked up to the end of that day.
3. **Valuation in CHF.** For one customer: each account's balance converted to CHF, once at the rate valid when each posting was booked (the sum of amount times that rate, posting by posting) and once at the latest rate, and the difference between the two. Use the latest `exchange_rate` row with `valid_from <=` the point in time. CHF postings need no rate. An account whose currency has no rate must still appear, with null values, not disappear. Say in the code comment whether you use inverse rates.
4. **Bank reconciliation.** A bank line matches an unmatched posting of the same account with the same amount whose booking date (UTC) is within two days of the line's value date; closest date first, every posting and every line used at most once. Do the matching in SQL (set `matched_posting_id`), not by loading rows into Java. Running it twice must change nothing the second time. Then report, for an account and a date range, the bank lines without a posting and the postings without a bank line.
5. **IBAN as a type.** `account.iban` should be a Java type `Iban` (validates the format and the mod-97 check digits, rejects an invalid value on creation) everywhere in the Java code, not `String`. Do it through jOOQ code generation (a converter or forced type configured in the build), not by converting by hand in every query. Adapt the existing code and tests; the seed data and the FX clearing accounts must keep working.
6. **Other dialects.** For the roll-up (item 1) and the valuation (item 3), provide a method that returns the SQL string rendered for a given `SQLDialect`. Tests render both queries for POSTGRES, MYSQL, MARIADB and H2, assert that rendering works, and assert that no Postgres-only syntax leaks into the other three (for example `::` casts or `jsonb`). These are rendering checks only; no other database has to run. (The first version of this task named ORACLE and SQLSERVER. Those dialects exist only in jOOQ's commercial editions, so the open-source build cannot render them. Both runs hit this and are logged.)

Tests must show the interesting cases, not only the happy path: a three-level group tree with accounts at several levels, a cycle attempt, days without postings, a posting at midnight, a rate that changes between two postings, a currency without a rate, two bank lines competing for one posting, and the second reconciliation run.

Log in `RUN-LOG-2.md`, not in `RUN-LOG.md`.
